Analysis on the COS side: a Connect timed out is a TCP SYN with no answer — DNS, TLS, IAM and COS itself are not involved (COS throttling would return HTTP 503/429, never a TCP timeout). Your test confirms it: at 5 min the front 55.73.66.3:4208 answers with a Cleversafe 403 (expected without auth, path is open), at 32 min the SYN is dropped before reaching it. Postgres on 55.39.x uses a different path, so it is not affected.
There is no connection-count limit or time-limited session on COS. The Hikari "connection has been closed" is a separate symptom: idle TCP sessions reaped by a stateful firewall/NAT on the path. Recommend maxLifetime below the firewall idle timeout (e.g. 10–15 min) and keepaliveTime ~5 min.
Since the job worked for months, this is a network path regression.
